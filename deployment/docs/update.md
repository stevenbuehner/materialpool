# Update und Rollback

Im Laravel-LXC als root `update` ausführen. Der Updater sperrt parallele Läufe mit `flock`, liest die installierte Version aus `current/release.json` und die neueste stabile Version aus GitHub. Bei gleicher Version endet er ohne Änderung. Er lädt das beim Release-Tag veröffentlichte Archiv und dessen Prüfsumme, prüft SHA256 und Archivstruktur, bereitet ein neues Release mit `composer install --no-dev` vor und stoppt erst dann die laufenden Prozesse. Ein `git pull` findet nicht statt.

Vor der Migration erstellt er ein komprimiertes MariaDB-Backup unter `/srv/materialpool/shared/backups/pre-X.Y.Z-<UTC>.sql.gz`. Dann folgen Maintenance Mode, Worker-Stopp, `php artisan migrate --force`, `production:preflight`, `optimize`, atomarer Symlinkwechsel, Dienststart und `/up`-Healthcheck. Nach erfolgreichem Healthcheck übernimmt er auch das Updater-Skript aus dem neuen Release. Derselbe Migrationsaufruf gilt bei der Erstinstallation und jedem späteren Release; dabei verwendet der Installer sein bereits geprüftes Archiv ohne zweiten Download. Den ersten Admin fragt er erst nach erfolgreichem Releasewechsel ab. Die letzten zehn Deployment-Backups und vier Code-Releases bleiben erhalten; Shared-Daten und reguläre Laravel-/S3-Backups werden davon nicht berührt.

Nur beim ersten Release erzeugt der Updater ein fehlendes Passport-Schlüsselpaar im Shared-Storage. Ein bereits vollständiges Paar bleibt auch nach einem abgebrochenen ersten Versuch erhalten; ein einzelner fehlender Schlüssel führt zum Abbruch. Spätere Updates erzeugen oder ersetzen keine Passport-Schlüssel.

Scheitern Download, Checksumme oder Composer, bleibt das alte Release aktiv. Scheitert eine Migration, bleibt die Anwendung im Wartungsmodus; die Datenbank kann schon teilweise geändert sein. Fehler nach der Umschaltung setzen den Code-Symlink auf das vorherige Release zurück, lassen den Wartungsmodus aber bis zur Prüfung der Datenbank aktiv. Restore nur nach dokumentierter Auswahl des korrekten Backups und ausschließlich auf einer Testinstanz üben. `migrate:rollback` erfolgt nicht automatisch.

Manueller Code-Rollback im LXC: `sudo /usr/local/sbin/materialpool-update rollback 0.0.1`. Vorher `ls -1 /srv/materialpool/releases` und das Zielrelease prüfen. Danach `/up`, Login, Queue und Migrationszustand prüfen. Der Rollback wechselt den Anwendungscode; das zuletzt installierte Updater-Skript bleibt erhalten. Bei nicht abwärtskompatiblen Migrationen ist zusätzlich ein geprüfter Datenbank-Restore nötig.

Die bisherige Ubuntu-/MySQL-Produktionsinstallation unter `ops/production/` wird durch diesen Befehl nicht aktualisiert. Ein Umzug zwischen den Betriebsprofilen verlangt einen isoliert geprüften Daten- und Schlüssel-Restore.
